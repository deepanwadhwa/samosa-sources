# S19v: descriptor-bound SQLite integration under qualification

Current state: the workspace defaults to bundled SQLite3.53.4 and both core and
durable read-operation stores use the descriptor-bound adapter unconditionally.
The old pathname-reopen branches are removed. Standard normal and owned-code
sanitizer suites pass both platforms, and clean offline source-archive builds
pass both. Controlled core execution also pins its admitted durable-operation
directory identity; its replacement-race fixture passes normal and sanitizer
checks on macOS/Linux. The earlier opt-in notes below record qualification
history, not current build requirements. Remaining service, upload/watch lifecycle
and optional integration qualification still prevent a complete Sources release.

The opt-in `DESCRIPTOR_DB=1` build opens core `sources.sqlite3` and durable
`read-operations.sqlite3` through a retained private state-directory descriptor.
Database and rollback-journal opens, metadata checks, deletion and directory
sync remain relative to that descriptor. A private synthetic VFS namespace
delegates native Unix I/O and locking; per-thread syscall routing forwards
unrelated SQLite access to the original callbacks. Native deferred-descriptor
reuse is validated through actual descriptor metadata. Admission permits only
the two fixed database names, private regular single-link files, and at most64
active bindings per process. Temporary storage is memory; WAL opens are refused.

The explicit adapter fixture covers post-admission/pre-open directory replacement,
replacement during a connection, native writer interoperability, separate-process
writer exclusion across adapter connection opens/closes, actual SIGKILL journal
rollback, capacity release/recovery and unsafe database-file refusal. Normal and
nonrecovering ASan+UBSan tests pass Linux system SQLite and macOS explicitly linked
Homebrew SQLite. Integrated normal binding-pin, operation and reindex tests pass
both; integrated binding-pin/operation sanitizers pass both.

macOS system SQLite uses guarded I/O and does not qualify with this adapter.
Temporary guarded-descriptor experiments are excluded from the component. Build
selection is explicit, for example:

```
make sanitize-bound-db SQLITE_LIBS='-L/opt/homebrew/opt/sqlite/lib -lsqlite3'
make sanitize-operations DESCRIPTOR_DB=1 SQLITE_LIBS='-L/opt/homebrew/opt/sqlite/lib -lsqlite3'
```

Changing flags/library requires rebuilding existing binaries. The default store
path remains selected until reproducible dependency packaging, broader runtime
and failure qualification, and retirement of the replaced path are complete.
This checkpoint does not qualify all SQLite VFS features, a threaded authenticated
service, full filesystem capabilities, or a Sources release. Detailed terminal
run evidence and outstanding gates are in the rebuild verification document.

Integrated continuous watch and queue normal and sanitizer runs now pass both
platforms after moving rollback-journal setup after store busy-handler setup.
The common Sources build and adapter test track compiler/flags/library selection
in `build/.configuration`, rebuilding when it changes. The portable stamp uses
a one-second timestamp separation on configuration changes for older Make/filesystem
resolution; unchanged builds preserve the stamp. Independent fixture-only build
rules do not all track this stamp yet.
